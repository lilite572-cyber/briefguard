# Разбор двух ошибок: от пикселей до метрики

Команды ниже воспроизводят два случая из сохранённого запуска: пропуск при
выборке кадров и пропуск при проверке уже выбранного кадра.

## Запуск

Из корня проекта, после установки зависимостей по README:

```bash
python scripts/explain_case.py
python scripts/explain_case.py --clip s010000-distractor-forbidden_patch-12
```

Скрипт читает завершённый запуск, заново генерирует один ролик, проверяет его
хеш, повторяет выбор кадров и проверку для трёх методов. Он отклоняет результат,
если кадры, бриф, разметка или предсказание расходятся с сохранёнными данными.
В конце он заново считает recall по всем строкам выбранного бюджета.

## Первый ролик: проверяющий не получил нужный момент

`s010000-distractor-forbidden_patch-6`: запрещённая область видна в кадрах
**[8,14)** — это кадры 8–13 включительно, четверть секунды при 24 fps.

| Метод | Кадры внутри нарушения | Ответ проверяющего | Что произошло |
|---|---|---|---|
| Uniform | Нет | pass | Пропуск на этапе выборки |
| Change | Нет | pass | Пропуск на этапе выборки |
| Adaptive | 12 | fail | Нарушение выбрано и обнаружено |

Uniform выбирает `[6,18,30,42,54,66,78,90]`. Формула в `_uniform` из
`briefguard/sampling.py` берёт середину каждого из восьми сегментов ролика.
Участок [8,14) находится между двумя выбранными моментами.

Adaptive сначала ставит четыре опорных кадра `[12,36,60,84]`, затем добавляет
четыре по оценке локальной необычности с поправкой на временное расстояние.
Здесь кадр 12 — уже опорный. Поэтому этот пример **не доказывает**, что сработала
именно оценка необычности: для такого вывода нужна отдельная абляция.

Проверяющий в `briefguard/verifier.py` видит только переданные кадры. На кадре 12
запрещённый цвет занимает всю контрольную область, доля равна 1.0 и превышает
порог 0.08. Результат содержит требование `forbidden_element_absent` и кадр 12.

## Второй ролик: нужный момент выбран, но проверяющий слабее требования

`s010000-distractor-forbidden_patch-12`: событие занимает **[10,22)**.
Uniform выбирает внутри него кадр 18, change — 16, adaptive — 12.
Все три метода возвращают **pass**, хотя нарушение есть.

В этом варианте пятно занимает 4 пикселя из контрольной области 8×12:
`4 / 96 = 0.041666…`. Это меньше порога 0.08. Порог задан в коде заранее,
поэтому пропуск ожидаем. Увеличение числа выбранных кадров не исправит этот
конкретный пороговый дефект, пока новые кадры содержат такое же малое пятно.

Важно различать две вещи: `sampling_hit` отвечает, попал ли выбранный кадр во
временной интервал; `prediction` — нашёл ли проверяющий нарушение в пикселях.
Доступ к разметке появляется при оценке результата, после выборки и проверки.

## Как одна строка входит в итоговый процент

В `briefguard/metrics.py`, функция `score`, recall считается как количество
обнаруженных нарушений, делённое на количество роликов с нарушением.
При восьми кадрах пересчёт сохранённых строк даёт:

| Метод | Расчёт | Recall |
|---|---|---:|
| Uniform | 268 / 768 | 34.90% |
| Change | 335 / 768 | 43.62% |
| Adaptive | 319 / 768 | 41.54% |

Первый ролик добавляет adaptive одно обнаружение, а двум другим — ошибочное
одобрение. Второй добавляет всем трём ошибочное одобрение. Удачный отдельный
пример не означает победу на всём наборе.

## Что проверить самому

Запусти обе команды и найди в JSON поля `event_frames_selected`, `decision`
и `exact_saved_evidence_match`. Затем открой соответствующие случаи в демо.
Объясни без подсказки, почему кадр 22 во втором ролике уже не входит в событие
и почему первый пример не доказывает пользу оценки локальной необычности.

После самостоятельного разбора запиши наблюдения в `development_notes.md`.
Человеческая оценка разметки выполняется отдельно по инструкции `human_review.md`.
