# Как объяснить BriefGuard на интервью

**Текущая честная подача:** «Я поставил задачу для AI-assisted проекта о пропусках коротких
нарушений в видео. Codex с субагентами подготовил код и провёл локальный эксперимент.
В проекте сравниваются три стратегии выборки кадров; адаптивная пока не показала преимущества
над простой эвристикой изменений. Сейчас я разбираю реализацию и результаты».

Первую версию кода, протокол, тесты и анализ выполнили агенты. Личная проверка реализации
и человеческая разметка пока не зафиксированы. Не говори «я лично написал и проверил всё»,
если этого не было. В [development notes](development_notes.md) есть история решений,
исправленные ошибки и список действий для личной проверки.

После самостоятельного разбора добавь конкретный личный вклад: какой модуль изменил,
какую ошибку нашёл, какой запуск повторил и что получил. Запиши реальные наблюдения.
Не называй проект новой моделью, SOTA, проверенной системой для реальной рекламы
или воспроизведением официального InfoShot.

## Архитектура

Генератор создаёт несколько вариантов одного исходного ролика. Исходный seed определяет
группу: чистый вариант и все нарушения попадают в один split. Разметка хранится отдельно.
Стратегия получает только пиксели и выбирает индексы. Проверяющий получает только выбранные
кадры и одинаковый для всех бриф. Runner сохраняет ответ, кадры, хеш пикселей и ресурсы.
Оценка подключает разметку только после предсказания.

Uniform выбирает середины равных временных сегментов. Change ранжирует глобальные изменения
между соседними кадрами и разносит выбранные моменты во времени. Adaptive оставляет часть
бюджета для покрытия ролика, остальное выделяет по локальной необычности, нормализованной
медианой и MAD, с поправкой на временное расстояние. Он адаптируется к содержимому, но не
получает обратную связь от проверяющей модели.

## Что говорить о результате

Точные числа и интервалы находятся в README и `results/test/tables.md`; они генерируются из
реального запуска. Главный вывод: победы над слабым baseline недостаточно. Простая эвристика
дала более высокий наблюдаемый recall при меньшей стоимости предварительного анализа.
Интервал разности с ней включает ноль, поэтому нельзя утверждать ни доказанное превосходство
adaptive, ни доказанное превосходство change по качеству.

Все слабые нарушения построены так, что попадают ниже допусков пиксельного проверяющего.
Это заранее известный предел контрольного детектора. Он нужен, чтобы не спутать попадание
кадра в событие с настоящим обнаружением. Это не оценка возможностей GPT или другой VLM.

## Вероятные вопросы

| Вопрос | Ответ, который нужно понимать |
|---|---|
| Что сделал ты, а что AI? | Я дал постановку и ограничения; первую реализацию и запуски выполнили Codex и субагенты. Дальше перечислить только действительно выполненные мной проверки и изменения. Если их ещё нет — сказать это прямо. |
| Почему не обучал нейросеть? | Проверяем механизм выборки. Обучение добавило бы смешивающий фактор и потребовало других данных/ресурсов. |
| Где здесь новизна? | Не заявляю новый принцип. Вклад — проверяемая локальная реализация, контролируемое сравнение, честный учёт ресурсов и анализ границ. InfoShot/SynFlash уже близок к вопросу. |
| Почему одинаковое число кадров не означает одинаковую стоимость? | Change и adaptive читают все кадры для предварительного анализа; uniform этого не делает. В отчёте эта стоимость включена. |
| Зачем разделять source и clip? | Родственные варианты сильно зависимы. Разделение по отдельным клипам привело бы к утечке, а bootstrap по клипам занизил бы неопределённость. |
| Как считается интервал? | Парный bootstrap исходных source-групп с возвращением, одни и те же выбранные группы для всех методов; затем процентили разности recall. |
| Почему событие [start,end)? | Кадр end уже после нарушения. Пик изменения на исчезновении аномалии не гарантирует, что выбран аномальный кадр. |
| Что такое false approval? | Это явно выданный pass на нарушающем ролике. При отказе от решения он отличается от полного числа пропущенных нарушений. |
| Почему ноль false positives не доказывает надёжность? | Контрольных примеров мало и они простые; неопределённость и сдвиг распределения остаются. |
| Как защищён тест от подстройки? | До запуска коммитом сохранены хеши протокола, аналитического кода, конфигурация и test seed. Runner проверяет соответствие. |
| Что нужно для реального продукта? | Реальные ролики с разрешённым происхождением, человеческая временная разметка, общий VLM/OCR-проверяющий, другая камера/сцены, оценка бюджета и ошибок на новом тесте. |
| Почему нельзя обещать формальную гарантию отказа? | Здесь нет отдельной калибровки selective prediction и проверки её предпосылок. Уверенный текст LLM не является гарантией. |

## Самостоятельная подготовка

Начни с [разбора двух реальных случаев](walkthrough_ru.md) и команды
`python scripts/explain_case.py`: она проверяет выбранные кадры и предсказания
против сохранённого эксперимента.

Запусти тесты, открой replay, выбери пропуск и вручную проверь пересечение индексов с
интервалом. Затем проследи конкретную строку `predictions.jsonl.gz` до агрегата. Измени
параметр в отдельной копии и убедись, что исходный test отказывается выполняться при drift.
Для новой гипотезы создай новый протокол и новые seed; не выдавай повторно использованный
тест за неизвестные данные. Человеческий аудит в этом проекте пока не выполнен.
